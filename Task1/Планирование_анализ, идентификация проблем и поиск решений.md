# Планирование_анализ, идентификация проблем и поиск решений

## Проблемы

1. **Клиенты не получают заказ в B2C-сегменте:**
    > Клиенты жалуются менеджерам по продажам, что они не получили заказ и над их изделием работают уже несколько месяцев, хотя обещали закончить за три недели. Проблемы не на стороне производства: производственные мощности позволяют справиться с заказами и могут обеспечить двукратный рост.

    Производственных мощностей хватает, а значит проблема на стороне системы.

    `над их изделием работают уже несколько месяцев, хотя обещали закончить за три недели` - на основании этой инфомрации можно предположить, что заказы "зависают" уже после подтверждения (`MANUFACTURING_APPROVED`), т.е. в MES-системе, но качественной информации об инцидентах нет.

2. **Клиенты не получают заказ в B2B-сегменте:**
    > Добавились жалобы со стороны пользователей API. Представители компаний ежедневно сообщают, что не получили свои заказы.

    > Для этого компания открыла свой API, который MES использует для расчёта стоимости изделия. В этом сценарии заказ создаётся в CRM через получение сообщения из очереди от MES.

    Поток заказов B2B-сегмента усугубил ситуацию с обработкой заказов. Подробной информации об инцидентах так же нет.

    Flow B2B-заказа отличается от B2C-заказов: в CRM систему информация приходит от MES-системы через систему очередей. Потенциальной это может быть проблемы потерь заказов могут содержаться в этой цепочке интеграций.

3. **Прямые запросы в API MES-системы по B2B-заказам**:
   > ... компания открыла свой API, который MES использует для расчёта стоимости изделия. В этом сценарии заказ создаётся в CRM через получение сообщения из очереди от MES. 

    API для B2B-заказов реализовано на стороне MES-системы, что ещё больше нагружает её. Роль API в данном контексте - передача данных о заказах в CRM-систему.

    API взаимодействует напрямую с системой MES, потенциально может повлиять на нагрузку системы. Если на стороне API не реализованы защитные механизмы, то создаёт риск вывода из строя в случае внешних аттак. Кроме того, невозможно управлять ограничением производительности системы - во время высокой загрузки MES-системы API может оказаться недоступным.

4. **Медленная работа списка заказов:**
   > Участились жалобы от операторов: когда они заходят на первую страницу MES, система долго прогружается. На первой странице отображается список заказов в работе по статусам — это дашборд с фильтром. Раньше страница показывала все заказы, но это тормозило загрузку. Команда сделала фильтр по статусам и пагинацию, но это не помогло.

   Внедрение фильтра по статусам и пагинация не решило проблему с загрузкой списка заказов. Это значит что либо при построении списка используются тяжёлые запросы (выполняющие дополнительные вычисления), либо СУБД испытывает высокую нагрузку.

   На этом этапе можно предложить 2 варианта решения проблемы: внедрение кеширования, реализация CQRS-паттерна на стороне СУБД (тем более для размещения БД используются Managed-сервисы облака).

5. **Потери сообщений при взаимодействии через RabbitMQ:**
    > MES и CRM взаимодействуют друг с другом через RabbitMQ. Эту интеграцию реализовала команда «Александрита».
   
    С учётом проблем с процессом обработки заказа есть потенциальные потери сообщений между системами без правильной обработки. Например, использование паттерна Dead Letter Queue.

6. **Тяжёлые расчёты на стороне MES-системы**
    > MES рассчитывает стоимость производства изделия на своей стороне, приложение онлайн-магазина в расчётах не участвует. 
  
    > Скорость расчёта стоимости зависит от количества полигонов в 3D-модели и в среднем занимает 2-3 минуты. Если модель сложная и детализированная, время обработки может достигать 30 минут.
  
    MES система в данный момент самая нагруженная по расчётам и выполняемым функциям. Учитывая, что и API для B2B реализовано на стороне MES есть риск увечения латентности обработки запросов на всех стадиях обработки заказов.

    Стоит рассмотреть вынос некоторых функций в отдельный сервис, а так же внедрить ограничение потока данных через RabbitMQ в зависимости от загруженности сервиса.

7. **Shared-база для Shop API и CRM API**
   По диаграмме C4 видно, что Shop API и CRM API используют единую shared-базу. Потенциально это создаёт риск влияния сервисов друг на друга и создаёт лишнюю зависимость в разработке и релизах сервисов: зависимость от структуры данных, синхронность миграции БД при релизах.

   Стоит рассмотреть разделение БД и организации асинхронной коммуникации между сервисами. В перспективе это может привести и к разделению команд разработки этих сервисов.

8. **Отсутствие Observability**
    Исходя из существующей информации о проблемаъ по заказам можно сделать вывод о том, что в системе затруднён поиск ошибок и расследование инцидентов. Нет информации на какой стадии "зависают" заказы, в какой конкретно системе это происходит и по какой причине.

    Всё это происходит по причине отсутствия централизованной системы логирования, мониторинга и трассировки.

9. **Один инстанс каждого приложения**
    > Каждый из инстансов крутится как EC2. Каждое приложение имеет по одному инстансу.
    
    Система не является отказоустойчивой и выход из строя одного из инстансов означает нарушение обработки всех заказов.

    К тому же вариант разворачивания как EC2 ограниченивает горизонтальное масштабирование приложений.

10. **Один инстанс сервера баз данных**
    > Базы данных — это Managed services на Yandex Cloud. Базы данных имеют один инстанс, который работает на запись и на чтение.
    
    Есть риск нарушения работоспособности при выходе из строя единственного инстанса, а так же риск потери данных в случае аварии.
    Хотя размещение в управляемом сервисах Yandex Cloud позволят быстро масштабировать и использовать read-only хосты.

11. **Долгий релиз:**
    > Команда выпускает софт двухнедельными спринтами. Есть тестовое окружение, на нём QA-инженер прогоняет E2E-сценарии вручную. Если он обнаруживает баги уровня high или highest, то версию не деплоят на продакшн до их починки. Это часто приводит к значительным задержкам релиза. 

    Долгие релизы значительно увеличивают Time-To-Market нового функционала и внедрения исправлений. Возможно, нужно пересмотреть процессы разработки, тестирования, подготовки релизов в команде (внедрение стандартов разработки в команде, автоматизация тестирования, автоматизация деплоя в разные окружения). 

12. **CI/CD**
    > CI/CD реализован так: Деплой в dev-окружение осуществляется автоматически после мёрджа пул-реквеста и прохождения юнит-тестов. В release-окружения версию деплоят вручную. В продакшн версию тоже деплоят вручную.

    Ручной деплой в release- и prod- окружение - достаточно трудоёмкий процесс (с учётом разворачивания приложений как EC2) и могут занимать длительное время. То же самое касается и процессу отката на предыдущие версии приложений. Рекомендуется автоматизировать ручной деплой, используя GitOps-подход.

13. **Тестирование**
    > Команда выпускает софт двухнедельными спринтами. Есть тестовое окружение, на нём QA-инженер прогоняет E2E-сценарии вручную. Если он обнаруживает баги уровня high или highest, то версию не деплоят на продакшн до их починки. Это часто приводит к значительным задержкам релиза. 

    Проблему задержек релизов так же возможно решить автоматизацией тестирования. Раннее обнаружение ошибок с помощью автоматизированных сценариев.

    Использование автоматизированного Unit-тестирования позволит выявлять ошибки ещё на стадии разработки.

14. **Команда**
    
    **Фронтенд**
    > Фронтенд — два инженера Vue, один частично знает React.

    Фронтенд MES построен на React - есть риск, что не хватит компетенций для выполнения какой-либо задачи.

    **Роль DBA**

    Возрастает нагрузка на БД, в команде нет отдельного специалиста. Скорее всего эту роль берёт на соебя либо TeamLead, либо DevOps. В связи с загруженностью по основным направлениям работы есть риск некачественного администрирования подсистемы управления БД.

    **QA-тестировщик**
    > QA — один инженер по ручному тестированию, хочет заняться автоматизацией и уже делал несколько прототипов.

    > Есть тестовое окружение, на нём QA-инженер прогоняет E2E-сценарии вручную. 

    У тестировщика есть желание расти и внедрять автоматизированное QA-тестирование, но тесты продолжают прогоняться вручную. Отсюда есть риск потерять специалиста по тестированию.

    **SRE-инженеры**

    Отсутствует команда по организации поддержки, качественного разбора инцидентов, маниторинга системы и других функций.    


## Инициативы, которые необходимы для устранения нежелательных ситуаций

### Горизонтальное масштабирование сервисов и СУБД

Каждый сервис системы (в том числе СУБД) имеет всего один инстанс, что не позволяет обеспечить должный уровень отказоустойчивости системы.

Для разворачивания сервисов и гибкого управления масштабированием предлагается использовать кластер Kubernetes. В рамках инициативы требуется проанализировать каждый сервис на готовность к горизонтальному масштабированию и возможность разворачивания в условиях кластера Kubernetes. 

Так же требуется развернуть сервис RabbitMQ в режиме кластера (High Availability, HA).

Что касается СУБД - базы данных уже размещены в Managed-сервисах Яндекс Облако, которые позволяют построить отказо-устойчивый кластер с минимальными затратами времени. Кроме того, это позволит использовать паттерн CQRS, поскольку в сервисах есть поддержка readonly-инстансов СУБД.

Эта инициатива направлена на повышение общей отказоустойчивости системы посредством дублирования отдельных компонентов.

### Реализация отдельного API для B2B-заказов

Цель инициативы - снизить нагрузку на MES-систему и изолировать функцию получения заказов по API в отдельном сервисе. Сервис должен обеспечивать обработку запросов от партнёров и передавать их в CRM-систему, используя асинхронную коммуникация с использованием RabbitMQ (тем более что у команды уже есть опыт построения подобных коммуникаций между MES и CRM).

### CQRS-паттерн

Исопльзование Managed-сервисов в Яндекс Облако для размещения баз данных предоставляет возможность использования readonly хостов и таким образом снизить нагрузку на мастер-хост.

В рамках инициативы нужно в сервисах перевести запросы чтения на readonly-подключения.

### Реализации кеширования

Медленная работа списка заказов может быть связана: с тяжёлыми запросами на получение этого списка, дополнительными расчётами на стороне СУБД при чтении, высокой нагрузкой на СУБД. Решить проблему с быстрым доступом к данным можно в том числе внедрением кеширование. 

В сервисах необходимо реализовать методы работы с кешом на стороне сервера, обеспечить корректную инвалидацию кеша. Кроме того, можно рассмотреть кеширование на стороне клиента для некоторых сценариев.

### Проработка стандартов асинхронной коммуникации сервисов

Использование асинхронной коммуникации между сервисами требует аккуратной обработки всех исключительных ситуаций (падение сервиса, некорректный формат запроса, нарушение бизнес-логики обработки запросов). В связи с этим рекомендуется проработать внутренние стандарты и рассмотреть применение таких паттернов как:

- DLQ: отдельная очередь для проблемных и ошибочных сообщений;
- Event Registry: единый регистр с описанием форматов запросов для использования валидации в сервисах;
- Backpressure: ограничение отправляемых данных в зависимости от производительности сервиса-потребителя (consumer).

### Распил MES-монолита на микросервисы

MES - сильно нагруженная система и есть смысл рассмотреть выноса функционала в отдельные микросервисы.

Например, функция расчёта стоимости модели изделия. Расчёт занимает много времени и имеет смысл изолировать функцию от обработки подтверждённых заказов. Это позволит снизить влияние тяжёлых расчётов на остальные функции MES-системы.

На первом этапе можно рассмотреть вариант разворачивания отдельного инстанса под эту функцию: без изменения кода просто отдельный экземпляр сервиса.

### Изоляция сервисов Shop API и CRM API

Сервисы Shop API и CRM API работают с единой базой данных, что вносит определённые ограничения на их разработку, подготовки релиза и деплоя. Рекомендуется разделить базы данных для этих сервисов и реализовать их интеграцию через RabbitMQ, а не через shared-базу.

Учитывая инициативу по разработке отдельного B2B API и интеграции его с CRM API это так же позволит снизить влияние на работу сервиса shop API.

### Внедрение Observability-платформы

Внедрение Observability позволит мониторить текущее состояние системы, выявлять "болевые" точки, находить причины сбоев и работать над стабильностью системы:

- Мониторинг метрик позволит увидеть наиболее загруженные участки системы и разработать методы решения проблем (горизонтальное или вертикальное масштабирование, внедрение кеширования и др.).
- Витрина логов сервисов позволит легче разбирать ошибки и сбои, возникающие в сервисах, увидеть контекст возникновения ошибки.
- Трейсинг позволит легче разбирать инциденты, связанные с обработкой заказов. Увидеть момент сбоя бизнес-процесса обработки заказов.

### Автоматизация тестирования

Внедрение автоматизированных тестов на всех этапах от разработки до деплоя нового релиза позволит не только снизить объём ручного тестирования, но и выявлять ошики на ранних стадиях разработки нового функционала. Ещё на этапе Unit-тестов в момент отправки MergeRequest/PullRequest в автоматическом режиме выявлять баги.

### CI/CD

Автоматизировать ручной деплой в release и prod, превратив его в запуск одобренного изменения (через GitOps).

Release-окружение: ввести промежуточную стадию или упростить ручной запуск. Например, GitOps-подход с ручным триггером: создать отдельную ветку или тег (например, release v1.2.3.). В инструменте CI/CD настроить процесс отслеживания этой ветки и деплоя в release-окружение:
- Ручное действие - создание тега или мёрдж в release-ветку;
- Автоматизация - инструмент применяет изменения.

Prod: важно сохранить ручной контроль, но сделать его более прозрачным и отслеживаемым. Использовать GitOps: продакшн-конфигурация лежит в отдельном репозитории (или защищённой ветке), инструмент CI/CD применяет только то, что закоммичено:
- Любое изменение в проде - pull request + code review + одобрение.
- Автоматизировать rollout strategy: использовать различные стратегии деплоя в зависимости от ситуации.
- Добавить health checks и автоматический rollback при падении метрик (через Observability-платформу).

### Команда

В команде предлагается ввести некоторые изменения:
- **Фронтент** - рассмотреть вакансию React-разработчика на MES-систему. Поскольку в команде есть только частичные компетенции по этому фреймворку и это создаёт риски для сроков и качества разработки.
- **Роль DBA** - нужно оценить компетенции DBA в команде. Предположительно эту роль совмещают DevOps и TeamLead разработки. Если компетенций недостаточно или загрузка этих сотрудников слишком большая - рассмотреть открытие вакансии.
- **QA-тестировщик** - в команде уже есть тестировщик, который умеет писать автоматизированные тесты. Имеет смысл его рассмотреть на роль QA-автоматизатора, а на роль мануального тестировщика открыть новую вакансию. Таким образом увеличим фокус на автоматизации тестирования без ущерба ручному тестированию, а так же увеличим лояльность QA-тестировщика.
- **SRE-инженер** - рассмотреть вакансию SRE-инженера для организации качественной эксплуатации всех компонентов системы (поддержка, мониторинг систем, участие в разборе инцидентов).

## Инициативы в порядке приоритета

Все инициативы можно разделить на несколько больших этапов. Сначала реализуются инициативы, закрывающие самые критичные вопросы системы: масштабирование и observability. 

Затем, имея уже данные мониторинга и представление о том что происходит с системой, а так же количество инстансов каждого из сервисов, соответствующее реальной нагрузке, можно переходить к оптимизации работы отдельных сервисов. 

Вынос B2B API в отдельный сервис, реализация кешировани и CQRS-паттерн - всё это в первую очередь напралено на снижение нагрузки и повышение производительности MES-системы. Кеширование и CQRS-паттерн не самые трудоёмкие задачи, поэтому их можно выполнить в первую очередь, а дальше уже переходить к выносу API из MES-системы.

На этом этапе система уже обладает свойствами отказоустойчивости и наблюдаемости. Мы знаем что происходит в системе и оптимизировали работу MES-системы. Для дальнейших действий требуется провести изменение в команде и провести автоматизацию процессов CI/CD и тестирования. Это позволит обеспечить функцию SRE отдельным человеком (а не всей командой сразу), повысить качество кода и выявлять баги на ранних этапах производства функционала, ускорить и повысить контроль деплоя сервисов (с учётом возросшего количество инстансов и планов на новые сервисы).

Дальнейшие шаги направлены на развитие архитектуры системы: распил MES-монолита, разделение сервисов Shop API и CRM API, и возможно другие, новые сервисы.

Порядок инициатив:

1. Внедрение Observability-платформы
2. Горизонтальное масштабирование сервисов и СУБД
3. Реализации кеширования
4. CQRS-паттерн
5. Реализация отдельного API для B2B-заказов
6. Проработка стандартов асинхронной коммуникации сервисов
7. Команда
8. CI/CD
9. Автоматизация тестирования
10. Распил MES-монолита на микросервисы
11. Изоляция сервисов Shop API и CRM API

В первые пол-года я бы сконцентрировал своё внимание на:
- свойствах масштабируемости и наблюдаемости всей системы. Это основа, от которой зависит дальнейшее её развитие;
- реализации паттернов кеширования и CQRS, что позволят снизить нагрузку на систему управления БД;
- выделение B2B API в отдельный сервис.

Эти шаги дадут наибольший эффект с точки зрения текущих известных проблем системы и это выполнимые задачи в горизонте пол-года.

В случае ограничения "не более 3х инициатив" стоит реализовать следующие:
1. Внедрение Observability-платформы
2. Горизонтальное масштабирование сервисов и СУБД
3. Реализации кеширования
