# Выбор и настройка мониторинга в системе

## Мотивация

Добавление мониторинга в систему - это не только техническая "опция", а стратегическая необходимость с учётом текущих проблем и планов развития компании. Ключевые причины и выгоды с акцентом на бизнес- и архитектурные аспекты:

1. Повышение устойчивости и доступности систем
    - **Проблема без мониторинга:** Сбои выявляются только после обращений пользователей или падения сервиса.
    - **Решение:** Мониторинг в реальном времени (метрики CPU, память, диски, latency, ошибки HTTP/API) позволяет обнаружить аномалии до их превращения в инциденты.
    - **Бизнес-выгода:** минимизация downtime ведёт к сохранению доверия клиентов, соответствие SLA, снижение рисков штрафов или потерь продаж (особенно с учётом известных инцидентов в направлении B2B).
2. Поддержка принятия решений на основе данных
   - **Мониторинг не только «сигнализирует об ошибках», но и собирает данные по:** нагрузке и пиковым периодам, производительности отдельных компонентов (например, серверов, сервисов, СУБД), поведению пользователей (частота вызовов API, время сессий и т.д.).
   - **Бизнес-выгода:** объективная основа для приоритизации дорожной карты модернизации, аргументация инвестиций в масштабирование или рефакторинг.
3. Ускорение диагностики
   - При инциденте мониторинг + логирование + трейсинг позволяют быстро локализовать корень проблемы — не наугад, а по цепочке метрик/логов. Особенно в распределённых и микросервисных архитектурах, где взаимодействие между компонентами сложно.
   - **Бизнес-выгода:** сокращение простоев ведёт к росту эффективности внутренних процессов и удовлетворённости сотрудников.
4. Поддержка стандартов и контроль качества
   - Мониторинг можно использовать как обратную связь по качеству кода и архитектуры: рост ошибок после деплоя - необходимо усилить тестирование или ревью; высокая нагрузка на конкретный микросервис - сигнал к декомпозиции или кэшированию.
   - **Бизнес-выгода:** качество кода влияет и на количество ошибок не только в сервисах, но и в бизнес-процессах обработки заказов.

## Выбор подхода к мониторингу

Для мониторинга системы предполагается использовать гибридный подход:

- **Четыре золотых сигнала** - как основа для внешне-ориентированных сервисов;
- **RED (Rate, Errors, Duration)** - для HTTP-API сервисов;
- **USE (Utilization, Saturation, Errors)** - для инфраструктурных компонентов: базы данных, очереди RabbitMQ, S3, серверы, а так же вычислительно-нагруженные части сервиса MES-API

### Общая стратегия по типам компонентов

| Компонент | Подход | Обоснование |
|--|--|--|
| Shop API, B2B API, CRM API, MES API | RED + Золотые сигналы | Это точки контакта с пользователями или системами, поэтому критично отслеживать UX и надёжность сервиса. |
| CRM, MES | Золотые сигналы (на уровне клиент-серверных запросов) + фронтенд-метрики | Пользовательский опыт (UX) в приложениях селлеров (CRM) и производства (MES) напрямую влияет на операционную эффективность. |
| Shop DB, MES DB | USE | Базы данных - узкие места системы и контроль нагрузки и ошибок критичен. Важно знать насколько СУБД загружен работой (Utilization), запросы в очереди (Saturation) и количество ошибок (Errors). |
| RabbitMQ | USE + RED | На очередях построена асинхронная коммуникация между сервисами и важно отслеживать интенсивность обработки сообщений, количество сообщений в очередях |
| S3-хранилище | RED | Обмен файлами критичен для MES - важно отслеживать отказы и latency обработки запросов. |
| MES API (тяжёлые расчёты стоимости изделий) | USE + собственные вычислительные метрики | Процесс расчёта ресурсоёмкий процесс важно дополнительно отслеживать не только жив ли сервис, но и успевает ли сервис выполнять работу. |

### Метрики

1. Shop API, B2B API, CRM API, MES API

| Метрика | Зачем | Ярлыки |
|--|--|--|
| HTTP-запросы в секунду (Rate) | Понимание нагрузки, выявление аномалий (например, DDoS или резкий рост запросов от партнёров) | `service`, `endpoint`, `method`, `client_type` (mes, crm, shop, b2b) |
| HTTP-ошибки (4хх, 5хх) | Выявление проблем в бизнес-логике и в сервисах. Особенно 5хх - сбой в сервисе | `service`, `endpoint`, `status_code`, `error_type` (timeout, db, auth, validation) |
| Latency (p50, p95, p99) | Выявление задержек обработки запросов (например, >1-2 секунд). | `service`, `endpoint`, `quantile`, `client_type` |
| Saturation (очереди соединения) | Отслеживание очередей поднятия соединения. Например, пул соединений к БД. Рост очереди может приводить к росту latency и количества ошибок | `service`, `resource_type` (db_pool, http_workers) |
| User-facing errors | Процет запросов с ошибками от общего трафика. Метрика показывает реальное влияние на пользователей | `service`, `client_type` |
| Traffic (RPC или объём данных) | Отслеживание трендов использования сервисов, планирование загрузки ресурсов | `service`, `client_type` |

Дополнительно для B2B-API добавить ярлык:
- `partner_id` - чтобы мониторить метрики в разрезе API, а так же видеть ошибки в интеграциях с партнёрами

2. CRM, MES

| Метрика | Зачем | Ярлыки |
|--|--|--|
| Frontend error rate | Ошибки на стороне клиентского приложения напрямую влияют на пользовательский опыт | `app` (crm/mes), `page`, `browser`, `user_role` |
| TTI, FCP, LCP | Время загрузки страницы, время появление первого видимого элемента, время отображения самого большого видимого элемента - всё это показывает отзывчивость интерфейса пользователя | `app`, `page`, `user_role` |
| Backend request latency (из UI) | Отделить фронтенд-проблемы от бэкенд-задержек | `app`, `api_endpoint`, `user_role` |
| Session duration / drop-off rate | Может быть косвенным признаком проблем в UX, если пользователи часто закрывают приложение | `app`, `user_role`, `workflow_stage` (например, order_creation) |

3. Shop DB, MES DB

| Метрика | Зачем | Ярлыки |
|--|--|--|
| CPU, RAM, I/O utilization | Обнаружение проблем с нехваткой ресурсов | `db_instance`, `db_type` (shop, mes) |
| Connection saturation (использование пула подключений) | Отслеживание перегрузки пула подключений, что может привести к таймаутам и ошибкам в API | `db_instance`, `app_source` (crm-api, shop-api, mes-api) |
| Replication lag | Отслеживание задержек в репликации данных, что может привести к несогласованности данных | `db_instance`, `replica_role` |
| Slow queries (count, duration) | Отслеживание узких мест в логике (слишком тяжёлые запросы), необходимость оптимизации БД | `db_instance`, `query_hash`, `app_source` |
| Deadlocks / lock waits | Отслеживание блокировок и ожиданий блокировок. Высокий показатель может означать некорректную бизнес-логику приложения или проблемы с сервером | `db_instance`, `table`, `transaction_type` |
| Disk space / WAL growth | Предотвращение аварийной остановки | `db_instance` |

Для MES DB нужно добавить ярлыки:
- `query_type` (например, cost_calculation) - чтобы мониторить запросы в разрезе тяжёлых запросов, например, на расчёт стоимости изделия

4. RabbitMQ

| Метрика | Зачем | Ярлыки |
|--|--|--|
| Queue length (per queue) | Отслеживание скопившихся сообщений в очереди. Рост показателя означает проблему в consumer | `queue_name`, `exchange`, `message_type` (например, order_created, status_changed) |
| Consumer lag | Понимание насколько обработка отстаёт от поступления сообщений | `queue_name`, `consumer_group` (crm_worker / mes_worker) |
| Publish/consume rate | Отслеживание нагрузки | `queue_name`, `direction` (publish/consume) |
| Error rate (nack, reject, redeliver) | Выявление проблем в обработке (например, невалидный заказ) | `queue_name`, `error_type` |
| Node CPU, memory, disk saturation | Использование USE для инфраструктуры брокера сообщений | `node`, `resource_type` |


5. S3-хранилище

| Метрика | Зачем | Ярлыки |
|--|--|--|
| Request rate (GET/PUT/DELETE) | Отслеживание нагрузки на хранилище | `bucket`, `operation`, `client_app` (crm, shop, mes) |
| Error rate (4xx/5xx) | Отслеживание ошибок, которые потенциально могут привести к потере файлов | `bucket`, `operation`, `error_code` (например, 403, 503) |
| Latency (p99 upload/download) | Отслеживание скорости загрузки/скачивания файлов | `bucket`, `operation`, `file_size_bucket` (small / medium / large) |
| Throttling events | Достигнут лимит запросов и нужно шардировать или оптимизировать | `bucket`, `operation` |


6. MES-API (тяжёлые расчёты)

| Метрика | Зачем | Ярлыки |
|--|--|--|
| CPU utilization (по инстансам) | Мониторинг использования ресурсов CPU для расчётов | `instance`, `service` |
| Memory Usage / Garbage Collector pauses | Отслеживание использование памяти и возможных утечек памяти | `instance`, `gc_type` |
| Calculation duration (p95, p99) | Позволяет мониторить длительность расчётов | `calculation_type` (e.g., cost / feasibility), `complexity_level` (low / medium / high) |
| Calculation queue length | Мониторинг длины внутренней очереди для расчётов | `worker_pool`, `priority` |
| Cache hit ratio (если есть кэш расчётов) | Отслеживание эффективности работы кеша | `cache_type` (redis / local), key_pattern |

## План действий

1. Инфраструктура сбора и хранения:
   1. Развернуть единый observability-стек на базе Grafana Stack (Grafana + Prometheus).
   2. Настроить long-term storage для метрик (Thanos) со сроком хранения более 12 месяцев (для трендов и аудита).
   3. Развернуть alerting-инфраструктуру (Alertmanager).
   4. Настроить единый identity & RBAC через Grafana (интеграция с LDAP/AD), чтобы селлеры/инженеры имели доступ к «своим» дашбордам.
2. Реализация метрик в компонентах системы:
   1. Shop API, B2B API, CRM API, MES API: интеграция с OpenTelemetry SDK; экспорт метрик (RED); автоматическая генерация `service`, `endpoint`, `client_type` ярлыков.
   2. CRM / MES (UI): подключить OpenTelemetry Web SDK; сбор JS-ошибок, метрик загрузки, duration backend-запросов; привязка к `user_id` / `role`.
   3. БД (PostgreSQL): развернуть exporters (Postgres Exporter — через perfmon или кастомный скрипт); сбор USE + slow queries + replication lag.
   4. RabbitMQ: включить prometheus_rabbitmq_exporter; настроить мониторинг по очередям.
   5. S3: использовать встроенные метрики + s3-exporter; настроить синтетический тест: загрузка/чтение тестового файла каждые 5 мин.
3. Визуализация и алертинг
   1. Создать базовые дашборды: общий health-дашборд (все API, БД, очередь); дашборды по ролям: селлер (CRM), инженер (MES), партнёр (B2B API).
   2. Настроить базовый набор алертов (по принципу SLO-error-budget): error budget burn rate > 2x; queue length > 50 for >5 min; DB connection saturation > 85%; MES API p99 latency > 10s.
   3. Определить и зафиксировать SLO/SLI для ключевого workflow: SLI: % успешных заказов (HTTP 2xx) за 24 ч; SLO: 99.5%; Error budget: 0.5%.

## Показатели насыщенности по компонентам


1. API-сервисы (Shop API, B2B API, CRM API, MES API)
   
| Показатель | Порог (Жёлтый/Красный) | Почему так | Действие при превышении |
|--|--|--|--|
| HTTP-воркеров (пула веб-сервера) | 70% / 90% от `max_workers` | При 90% — новые запросы ждут в очереди, что ведёт к росту latency и таймауты.  | Жёлтый: автоматическое уведомление в чат. <br>Красный: создание тикета в поддержку с приоритетом 'High', автоматическое добавление инстансов. |
| Пул соединений к БД | 75% / 85% от `max_connections` | PostgreSQL начинают отклонять новые соединения при 100%, но уже при 85% — рост wait time и contention. | Жёлтый: алерт в мессенджер + сбор slow-query лога за последние 10 минут. <br> Красный: отправка уведомления, включение механизма rate-limitting (если реализован), создание тикета владельцу сервиса с приоритетом 'Blocker'. |

2. Базы данных (Shop DB, MES DB)
   
| Показатель | Порог (Жёлтый/Красный) | Почему так | Действие при превышении |
|--|--|--|--|
| CPU utilization (среднее за 5 мин) | 70% / 85% | Загрузка >85% ведёт к росту времени выполнения запросов, а у СУБД не остаётся свободных ресурсов CPU на фоновые задачи (vacuum, WAL). | Жёлтый: сбор `pg_stat_statements` / `dm_exec_query_stats`, топ 5 slow queries в дашборд.<br>Красный: тикет с приоритетом `High`, автоматическое уведомление в чат. |
| Connection saturation | 75% / 85% | Критично для сервисов с большим количеством пользователей и подключений | Жёлтый: алерт в мессенджер + сбор slow-query лога за последние 10 минут. <br> Красный: отправка уведомления, включение механизма rate-limitting (если реализован), создание тикета владельцу сервиса с приоритетом 'Blocker'. |
| Disk I/O saturation (await > 20 ms, util > 80%) | 70% / 90% | SSD - await > 20 ms означает перегрузку; HDD — не допускать >50%. | Красный: немедленное уведомление — риск полного зависания. |

3. RabbitMQ
   
| Показатель | Порог (Жёлтый/Красный) | Почему так | Действие при превышении |
|--|--|--|--|
| Длина критической очереди | n сообщений / m сообщений, где n и m определяются для каждой очереди (или группы очередей) | При n сообщений (жёртый) означает, что консьюмер не справляется. | Жёлтый: уведомление в чат, запуск проверки `consumer_lag`.<br>Красный:  |
| Memory used / high watermark | 80% / 90% | При достижении `vm_memory_high_watermark` (по умолчанию 40% RAM) — RabbitMQ начинает блокировать publishers. | Красный: экстренный дамп метрик + перезапуск ноды (только если кластер ≥ 3 нод). |

4. S3-хранилище
   
| Показатель | Порог (Жёлтый/Красный) | Почему так | Действие при превышении |
|--|--|--|--|
| Throttling rate (Put/Get) | >1% запросов / >5% | Даже 1% — это файлы не загрузились, а значит какой-то из процессов прервался с ошибкой | Жёлтый: уведомление в чат.<br> Красный: тикет в поддержку, включение fallback-хранилища (если есть). |

5. MES-API (тяжёлые расчёты)
   
| Показатель | Порог (Жёлтый/Красный) | Почему так | Действие при превышении |
|--|--|--|--|
| Очередь расчётов (internal channel/backlog) | 10 задач / 30 задач | 30 задач при расчёте 30 минут - это 15 часов ожидания расчёта. | Красный: уведомление в чат + уведомление пользователя в UI: «Система перегружена. Ваш расчёт задерживается» |
