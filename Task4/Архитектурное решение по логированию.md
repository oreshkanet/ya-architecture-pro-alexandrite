# Архитектурное решение по логированию

## Планирование логирования

###  Логи жизненного цикла заказа (изменение статусов)

**Системы-источники:** InternetShop, CRM API, MES API
**Цель:** аудит, аналитика времени обработки, диагностика "зависаний" заказов.

| Событие | Система | Лог (уровень INFO) |
|--|--|--|
| `INITIATED` | InternetShop | Order initialized: orderId={id}, customerId={cid}, timestamp={ts}, cartId={cartId} |
| `FILE_UPLOADED` | InternetShop | File uploaded for order: orderId={id}, customerId={cid}, fileName={name}, fileSize={size}, uploadId={uploadId} |
| `SUBMITTED` | InternetShop | Order submitted: orderId={id}, customerId={cid}, itemsCount={n}, totalAmount={amt} |
| `PRICE_CALCULATED` | MES API | Price calculated: orderId={id}, estimatedCost={cost}, calculationTimeMs={ms}, componentsCount={cnt} |
| `MANUFACTURING_APPROVED` | CRM API | Order approved for manufacturing: orderId={id}, approverId={uid}, comments={cmt} |
| `MANUFACTURING_STARTED` | MES API | Manufacturing completed: orderId={id}, durationSec={sec}, operatorId={uid} |
| `MANUFACTURING_COMPLETED` | MES API | Manufacturing completed: orderId={id}, durationSec={sec}, operatorId={uid} |
| `PACKAGING` | MES API | Packaging started: orderId={id}, operatorId={uid}, packagingType={type} |
| `SHIPPED` | MES API | Order shipped: orderId={id}, shippingProvider={sp}, trackingNumber={tn}, shippedAt={ts} |
| `CLOSED` | CRM API | Order closed: orderId={id}, closureReason={reason}, closedAt={ts}, finalStatus={status} |

Для всех INFO-логов статуса нужно также включать traceId, чтобы связать статусы с цепочкой вызовов.

### Логи интеграций (MQ, S3, API-вызовы)

Системы-источники: CRM API, MES API, Shop API, B2B API
Цель: отслеживание доставки сообщений, latency, согласованность данных.

| Событие | Система | Лог (уровень INFO) |
|--|--|--|
| Публикация события в RabbitMQ | CRM API / MES API | Published event to queue={q}: eventType={type}, orderId={id}, payloadId={pid}, timestamp={ts} |
| Получение и обработка события из RabbitMQ | CRM API / MES API | Consumed event from queue={q}: eventType={type}, orderId={id}, processingDurationMs={ms} |
| Загрузка/чтение файла из S3 | Любая (InternetShop, CRM, MES) | S3 file operation: action={upload}, orderId={id}, latency={mc} |
| API-вызов | Запросы между сервисами:<br> Shop API -> CRM API,<br> CRM API -> MES API<br> и т.п. | API call {method} {url} for orderId={id}: statusCode={code}, durationMs={ms}, retryCount={n} |

### Логи операций с сессией и аутентификацией

Системы-источники: InternetShop, CRM, MES
Цель: безопасность, аудит действий пользователей.

| Событие | Система | Лог (уровень INFO) |
|--|--|--|
| Успешный логин | CRM / MES / InternetShop | User login: userId={id}, role={role}, ip={ip}, userAgent={ua} |
| Выход из системы | CRM / MES | User logout: userId={id}, sessionDurationSec={sec} |
| Создание/редактирование заказа оператором | CRM / MES | Order modified by user: orderId={id}, userId={uid}, action={created/updated} |

### Логи запуска и завершения сервисов

Системы-источники: Все backend-сервисы (Shop API, CRM API, MES API, B2B API)
Цель: мониторинг деплоев и аварийных остановов.

| Событие | Система | Лог (уровень INFO) |
|--|--|--|
| Старт сервиса | Все API | Service {name} started. Version={v}, env={env}, DB={dbHost}, commit={sha} |
| Остановка сервиса (graceful) | Все API | Service {name} shutting down gracefully |

### Другие уровни логирования: когда и зачем

| Уровень | Когда использовать | Примеры |
|--|--|--|
| `DEBUG` | Для диагностики в dev / staging; можно включать временно в prod при инциденте | - Детали расчёта в MES API<br>- Тело запросов/ответов обезличенное (без PII, без паролей)<br>- SQL-запросы (без параметров) |
| `TRACE` | Только для глубокого профилирования/отладки; почти никогда не включать в продакшен | - Пошаговая трассировка алгоритма калькуляции<br> - Поток выполнения в сложном бизнес-процессе |
| `WARN` | Важные, но некритичные события, требующие внимания | - Попытка повтора отправки в RabbitMQ<br> - Замедление S3-операции (>5s)<br> - Неизвестный статус заказа при синхронизации |
| `ERROR` | Ошибки, прерывающие бизнес-процесс, требующие реакции | - Падение API-вызова к зависимому сервису (после N ретраев)<br> - Невозможно обновить статус заказа в БД<br> - Невалидная 3D-модель (пользовательская ошибка — ERROR, если не перехвачена на UI) |
| `FATAL` | Серьёзные сбои, делающие сервис неработоспособным | - Недоступность БД при старте<br> - Отказ кластера RabbitMQ |

## Мотивация

Сейчас система состоит из нескольких независимых сервисов, интегрированных через HTTP и RabbitMQ, с десятью статусами заказа, разбросанными по разным доменам. При этом:

- известны проблемы о зависаниии заказа на каком-то этапе — и диагностика требует ручного сопоставления данных из разных БД и логов (если они есть);
- нет сквозного понимания времени обработки заказа (SLA нарушается, но причина неясна);
- при инцидентах (например, "заказ не ушёл в производство") расследование занимает много времени;
- бизнес не видит "бутылочных горлышек" в процессе: где теряется больше всего времени.
- 
Логирование — это не "отладка для разработчиков", а компонент observability-платформы, необходимой для:

- снижения MTTR (Mean Time To Resolve) инцидентов,
- повышения прозрачности процессов для product- и operations-команд,
- объективной оценки эффективности — как технических компонентов, так и человеческих действий (например, время принятия решения селлером).

### Технические и бизнес-метрики, на которые повлияет логирование

| # | Метрика | Как измеряется | Эффект от логирования |
|--|--|--|--|
| 1 | MTTR (Mean Time To Resolve) | Среднее время от фиксации инцидента до устранения | Сократится за счёт быстрого локализации корневой причины |
| 2 | Order Cycle Time (OCT) | Время от `INITIATED` до `CLOSED` | Станет измеримым и детализируемым: можно будет выделить этапы с наибольшей задержкой и оптимизировать workflow заказа |
| 3 | Согласованность данных между системами | Доля заказов с расхождением статусов в CRM и MES | Снизится за счёт аудита событий через логи, а так же выявления "потерянных" сообщений в очереди |
| 4 | Коэффициент автоматизации обработки заказа | Доля заказов, прошедших от `SUBMITTED` до `MANUFACTURING_APPROVED` без ручного вмешательства | Станет измеримым и можно будет оценивать эффект от внедрения автоматизации |
| 5 | SLA compliance (для B2B) | Процент заказов, обработанных в рамках договорного времени | Появится объективная отчётность и возможность оценитвать риск срыва сроков заказов (и потенциальное получение штрафов по условиям договора) |


### Приоритетные системы для логирования и трейсинга

Команда не может реализовать всё сразу. Поэтому предполагается этапный подход, основанный на риске, стоимости ошибок и потенциале улучшений.

1. MES API + CRM API

Обоснование выбора:

- В этих сервисах происходят ключевые бизнес-события: расчёт цены, подтверждение, производство, отгрузка — всё, что влияет на сроки и себестоимость.
- На основании имеющейся информации заказы зависают и теряются где-то здесь
- Между этими сервисами самая хрупкая интеграция (RabbitMQ), где чаще всего могут теряться заказы.
- MES API — единственная точка, где выполняются ресурсоёмкие расчёты: логи помогут выявлять узкие места.

В первую очередь внедряются:

- Сквозные traceId во всех логах и сообщениях RabbitMQ;
- INFO-логи смены статусов (все, кроме `INITIATED`, `FILE_UPLOADED`, `SUBMITTED`);
- WARN/ERROR при ошибках расчёта, таймаутах, недоступности БД;
- Логи публикации/потребления событий в RabbitMQ.

2. Shop API + B2B API + InternetShop

Обоснование выбора:

- Это точки входа заказов — зона наибольшего риска потерь.
- B2B API — критичен для корпоративных клиентов: сбои здесь - прямой ущерб репутации и доходу.
- InternetShop генерирует первые 3 статуса — без них невозможно отследить "брошенные" заказы.

Список к внедрению:

- INFO: `INITIATED`, `FILE_UPLOADED`, `SUBMITTED` с traceId
- Логи внешних вызовов CRM API (включая retries)
- Логи загрузки файлов в S3 (размер, тип, duration)
- ERROR: валидация модели, ошибки оплаты (без реквизитов), сбои API

3. CRM и MES (фронтенд)

Обоснование:

- Менее критичны для сквозного трейсинга, но важны для аудита действий пользователей (селлеров, операторов).
- Позволяют ловить "человеческий фактор": например, заказ ждёт 8 часов, потому что селлер забыл нажать "Подтвердить".

Список к внедрению:
- INFO: вход/выход, изменение заказа (кто, что, когда), экспорт/печать;
- WARN: медленные запросы к API (>3s), ошибки загрузки файлов;
- Интеграция traceId из backend-ответов в фронтенд-логи (через заголовок `x-trace-id)`.

## Предлагаемое решение

Для централизованной системы сбора и хранения логов предлагается решение, разбитое на три слоя: генерация, сбор и агрегация, анализ и хранение.

### Генерация логов (внутри сервисов)

В коде каждого сервиса выполняется реализация модулей генерации логов на основе требований:
- реализация структурного логирования в JSON;
- включение в логи полей трассировки и контекстных полей: traceId, spanId, userId, orderId, requestId;
- внедрение фильтров чувствительных данных;
- добавление метаданных среды: env=prod, region=ru-central-1, version=1.4.2, git.commit=abc123.

### Сбор и агрегация

| Компонент | Роль | Обоснование выбора |
|--|--|--|
| Fluent Bit (sidecar в Kubernetes / агент на VM) | Лёгкий сборщик логов, парсинг JSON, фильтрация, буферизация | Меньше overhead, чем Fluentd; поддержка OpenTelemetry Protocol (OTLP); встроенная маскировка полей. |
| Kafka | Буферизация логов и снижение связанности между сервисами и системой хранения логов | Гарантирует доставку при пиковых нагрузках (например, массовая загрузка заказов); позволяет повторно обработать логи при сбое индексации. |
| Grafana Loki | Хранение и индексация (на основе label-based индекса) | Дешевле ELK, лёгкий, отлично интегрируется с Grafana; поддержка traceId-поиска; сжатие логов. |
| Grafana | Визуализация, дашборды, алертинг | Единый UI для логов |

### Политика безопасности

- **Запрет логирования PII по умолчанию:** В коде — жёсткие code review и статический анализ кода (например, настройка правила: "не логировать email, phone, inn, cardNumber");
- **Маскировка в runtime:** в Fluent Bit использовать modify + mask операторы или lua-скрипты для замены (например: "email": "user@***");
- **Шифрование на транспорте:** TLS 1.3 между всеми компонентами (Fluent Bit -> Kafka -> Loki);
- **Ограничение доступа к логам:** обязательна настройка RBAC в Grafana.

### Политика хранения

| Параметр | Рекомендуемая настройка | Обоснование |
|--|--|--|
| Формат хранения | Структурированный JSON (logfmt/json) | Поддержка фильтрации по полям, эффективный поиск. |
| Индексация | - По label’ам: `service=crm-api`, `env=prod`, `status=ERROR`<br> - Отдельный индекс/стрим на каждую систему + среду: `logs-crm-api-prod-2025.12.06` | Баланс между гибкостью и стоимостью: легко очищать, ротировать, ограничивать права. |
| Срок хранения | - `INFO/WARN`: 30 дней<br> - `ERROR/FATAL`: 180 дней<br> -`DEBUG/TRACE` (если включены): 7 дней | Соответствует требованиям большинства стандартов (PCI DSS — 1 год для аудита, но можно архивировать в холодное хранилище); 30 дней — достаточно для анализа трендов и SLA |
| Холодное архивирование | Автоматическая ротация ERROR-логов в S3 через 180 дней с шифрованием | За счёт использования S3 хранение дешевле |
| Оценка объёма | ~2–3 GB/мес в Loki | Логика расчёта: - 10 000 заказов/день<br> - ~50 лог-записей/заказ (с учётом API-вызовов, MQ, статусов)<br> - ~1 KB/запись (JSON)<br> - ~500 MB/день<br> - ~15 GB/месяц (сжатие Loki даёт 5–10×)<br> - ~2–3 GB/мес в Loki |


## Превращение системы сбора логов в систему анализа логов

Сбор логов — это пассивное наблюдение. Анализ — это активное извлечение знаний, позволяющее принимать решения до того, как клиент пожалуется или встанет обработка заказов.

Для этого нужно внедрить три ключевых компонента:

1. Правила и алертинг (реакция на известные паттерны):
   
    Алерты должны быть ситуационными, действенными. Можно разделить по нескольким категориям:
    - **Инциденты** - отслеживание интенсивности возникновения ошибок в сервисах;
    - **Бизнес-нарушения** - отклонения в бизнес-процессе обработки заказов (нарушение последовательности, задержка в одном статусе);
    - **Интеграционные сбои** - рост ретраев при отправке запросов, рост количества сообщений в очередях RabbitMQ;
    - **Безопасность** - отслеживание аутентификации (количество неудачных попыток входа);
    - **Производительность** - отслеживание среднего времени обработки запросов.

    Для каждого правила разрабатываются свои методы реакции: алертинг в мессенджер ответственным, автоматический скейлинг ресурсов (поднятие дополнительных инстансов), автоматическая блокировка IP (в случае подозрительных действий) и т.д.  

2. Анализ аномалий (обнаружение неизвестных угроз):

    - **Всплеск частоты событий:** например, рост с 4 до 1000 заказов/сек может означать DDoS-атаку или ошибку в партнёрской интеграции.
    - **Исчезновение событий:** например, отсутствие логов перехода заказа в статус `MANUFACTURING_STARTED` может означать либо проблему с MES-сервисами, либо проблему с интеграцией.
    - **Изменение распределения:** например, резкий рост заказов с определённм типом файлов может означать попытку атаки с целью перегрузить расчёт, используя битые файлы
    - **Зависание статусов:** например, 80% заказов застряли в статусе `PRICE_CALCULATED` более 1 часа может означать проблему в процессе расчёта 


3. Построение аналитических дашбордов и метрик (превентивная оптимизация).

    Дашборды позволяют анализировать общее состояние бизнес-процессов и выявлять потенциальные проблемы в системе.

    - **Жизненный цикл заказа:** тепловая карта со средним временем (и 95% персентиль) между статусами, процент дохождения заказов до определённого статуса. Позволяет выявлять узкие места в системе.
    - **Состояние интеграций:** latency процесса расчёта цены, процент повторных отправок в очередь, размер очередей. Позволяет контролировать интеграции.
    - **Операторская нагрузка:** Количество заказов в час на специалиста, время нахождения заказа между статусами (например, `MANUFACTURING_COMPLETED` и `PACKAGING`).
    - **Качество входных данных:** Процент заказов с ошибками валидации запросов API и валидации файлов. 

## Критерии выбора технологий

| # | Критерий | ELK | OpenSearch | Splunk | Grafana Loki |
|--|--|--|--|--|--|
| 1| Лицензия | SSPL (ограничивающая) | Apache 2.0 (свободная) | Проприетарная | Apache 2.0 |
| 2 | Архитектура | Монолитный индекс -> шарды | Как ELK, но с улучшенным управлением | Проприетарная (bucket -> index) | 3-tier: distributor -> ingester -> querier + storage (S3/GCS) |
| 3 | Стоимость владения (TCO) | Дорого: платные фичи (алертинг, безопасность), лицензия SSPL ограничивает облака | Бесплатно и открыто: всё enterprise — в OSS-сборке | Очень дорого: плата за объём логов ($1.5–2K за 1 ГБ/день) | Очень дёшево: open-source, хранение в S3, минимум ресурсов |
| 4 | Поддержка распределённого трейсинга | Хорошая:<br>- traceId индексируется как .keyword<br>- Kibana APM (только в paid tiers)<br>- Интеграция с Jaeger через сторонние плагины | Хорошая:<br>- Аналогично ELK — traceId как keyword<br>- OpenSearch Observability plugin — бесплатно<br>- Поддержка OTel Collector | Лучшая (но дорого):<br>- Автоматическое связывание логов/метрик/трейсов<br>- мгновенный поиск по trace_id, визуализация цепочки<br>• Splunk APM — включено в лицензию | Оптимальная для event-driven систем:<br>- traceId - поиск по label за O(1)<br>- Встроенный переход в Grafana Tempo (трейсинг)<br>- Высокая скорость поиска LogQL |
| 5 | Эффективность хранения | Неэффективна для логов:<br>- Full-text индекс, который требует большого хранилища ×2.5–3.5<br>- Поиск по `orderId` требует keyword-поля<br>- Холодное хранилище — только в Platinum | Улучшено:<br>- Поддержка ultrawarm и cold tier бесплатно<br>- Index state management (ISM) — автоматическая ротация<br>- Сжатие как у ES | Высокая :<br>- SmartStore (данные в S3, метаданные локально)<br>- Дедупликация, сжатие до ×5 | Высокая эффективность:<br>- Label-based индекс (только метаданные)<br>- Тело лога — сжатый чанк (gzip + snappy)<br>- Общий объём: ~10% от сырых логов<br>- Поиск по label — мгновенно; поддержка full-text поиска |
